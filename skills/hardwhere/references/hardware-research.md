
# Hardware research and wiring

1. Convert the goal into measurable inputs, outputs, range and response time. Capture useful constraints such as existing parts, power, enclosure, bus length and budget. Look for the simplest board and module that meet them. Explain the selection, include power, cabling and interfacing parts in the BOM, and give a first test the user can observe.
2. Identify the board, PCB revision, module and chip separately. Use silkscreen, photos, markings and USB evidence. USB IDs often describe a bridge or shared bootloader. For an unidentified board, compare against manufacturer drawings and ask for the one marking or observation that resolves the ambiguity.
3. Find manufacturer board pinouts and schematics, chip and module datasheets, and official SDK documentation. Read the relevant pages or tables, including package variants, pin multiplexing, absolute maximum ratings and recommended operating conditions. Cross-check a breakout schematic against the raw chip datasheet. Link the document, revision and page or section behind the wiring or tool decision. Record unresolved details. When a document is available only as an image, inspect the actual pinout and orientation before assigning pins.
4. Check direction, signal voltage, available regulated current and return path. Account for logic thresholds, required pull-ups or level shifters, boot straps, reserved pins, I²C address, alternate functions, and connector orientation when relevant. Use the recommended operating range for design. Avoid powering or instructing the user to energize wiring that depends on an unresolved pinout, supply or voltage limit.
5. Present exact header labels first, GPIO or physical header numbers alongside them, and a separate note on the power source. Tell the user which side of the board the drawing shows. For adjustable addresses, state the expected setting. Give a power-off check and one bring-up test.

Use `hardwhere wiring wiring.json` for a table and Mermaid diagram from one source. Each item in `wires` has `from` and `to` arrays containing `[component, pin label]`, plus `signal`, `voltage_v`, `max_voltage_v`, and a `source` citation. For shared bus lines, encode the lowest safe limit of all endpoints. This renders documentation and checks entered voltages against entered limits. Check current, logic thresholds, pull-ups and electrical function against the sources. When splitting grounds, using an isolator or adding a translator, represent the separate nets explicitly.
