
# Bench workflow

1. Run `hardwhere profiles --json`, `hardwhere discover --json` and `hardwhere doctor --board <id> --json`. Match the board marking to the profile and the USB path to the intended physical board. If needed, unplug only that board and compare before and after. Treat a shared VID/PID as a candidate. For new chip families, look up the official programmer, connection mode and recovery procedure. Explain the documented method and use the vendor tool directly if it can identify the target and the user authorizes the operation.
2. Interpret the missing dependency at the right layer. The host driver exposes the USB interface. The board core or SDK builds firmware. A firmware library speaks the sensor's protocol. On Linux check permissions and the bound kernel driver. On macOS check enumeration and any vendor installation prompts. On Windows use the bridge VID/PID and device problem state before installing an official INF. If the driver is already bound, investigate the cable, permission or application. Use the official archives and platform-specific installation steps for vendor tools.
3. Compile for the exact board with a new artifact directory and report the toolchain. For writes, check the selected target, artifact and user authorization. Use `--apply` as part of the authorized command. For Teensy 4.1, ask the user to confirm the model by silkscreen, disconnect other Teensys and press the Program button on the intended device. Then discover the HalfKay HID target and flash once. Close serial monitors before upload. Ask again only if moving outside the action the user authorized, such as a full erase or recovery operation.
4. After upload, rediscover if needed. Run a bounded serial capture or `verify --expect` against a full line produced by the active test. Record firmware upload separately from behavior. If the output could come from earlier firmware, change the sample marker or ask for a reproducible response to a physical stimulus. A fixed boot banner establishes that firmware starts. A plausible repeated measurement plus a controlled change at the sensor establishes much more about the circuit.
5. Debug one variable at a time. First record the exact error and last stage that passed. Choose a test that distinguishes the leading causes, for example USB re-enumeration for a port issue, serial boot logs for resets, a meter for supply sag, or a logic analyzer for missing I²C ACK. Verify I²C address and voltage before probing the intended bus. Use a documented SWD/JTAG workflow when the specific board, probe and pinout are confirmed. Stop retrying writes if a failure leaves the device state uncertain. Find the manufacturer recovery flow and identify the board again.

On Windows, if an installed Teensyduino compiler reports a missing GCC standard header such as `bits/c++config.h`, check the SDK data path. The reference build passed with a shorter path for the Arduino data directory and compiler temporary files.

For a checkpoint, write a JSON object with `board`, optionally `revision`, `modules`, `wiring`, `sources`, `tools`, `checks`, and `next_step`. In `checks` record the stage, status, and a short evidence summary. Run `hardwhere context save <file> --project <directory>`. The CLI stores it in the local `.hardwhere/` directory. Keep raw logs and access details out of project context and public issue reports.
